# Curriculum Graph (W6.4) — BLUEPRINT §20 v1.8

Status: MVP shipped 2026-05-13.
Scope: single-domain (AI / Computer Science) hand-curated DAG. Other
domains explicitly deferred — we do not attempt universal coverage.

## Why this exists

A general LLM asked "teach me transformers" will free-associate a list of
related buzzwords. It cannot reliably answer: "what must I have done first?",
"where in the field does this sit?", "what's the canonical exercise here?",
"what 2026 paper connects to this idea?". The curriculum graph gives the
system a hand-curated prior for those questions. Designed to produce
generation paths obviously stronger than vanilla ChatGPT for AI/CS topics.

## Surface

Files:
- `app/lib/curriculum-graph/ai-cs-graph.json` — seed graph (48 nodes, 6
  layers). Hand-curated. Never regenerated by an LLM.
- `app/lib/curriculum-graph/graph-engine.js` — pure functions over the graph.
- IPC (`app/main.js`): `curgraph:load` / `curgraph:findPath` /
  `curgraph:recommendNext` / `curgraph:kpForGoal` / `curgraph:frontierBridge` /
  `curgraph:buildCustom`.
- Preload (`window.ptor.curgraph.*`): mirrors the IPC verbs.
- UI (`app/design/screen-curriculum-graph.jsx` → `window.CurriculumGraphScreen`).
- Route in `app/design/app.jsx`: `"curriculum-graph"`.

## Graph schema

### Node

```json
{
  "id": "string-kebab-id",
  "name": "Human-readable name",
  "layer": "foundation | ml-classic | dl | llm | agent | builder",
  "prereq_ids": ["other-node-id", ...],
  "difficulty": 1,
  "canonical_example": "single-sentence concrete exercise",
  "assignment_types": ["derivation", "code-from-scratch", ...],
  "frontier_bridges": ["sentence connecting this KP to a 2025-26 frontier line"],
  "frontier_recommended_reading": ["author year + title or doc handle", ...]
}
```

### Edge

Edges are implicit: an edge from `A → B` exists iff `A ∈ B.prereq_ids`. The
graph is a DAG; cycles are rejected by `loadGraph` at load time.

## The 6 sub-domains (layers)

| Layer            | order | Spans                                                                  |
|------------------|-------|------------------------------------------------------------------------|
| foundation       | 0     | Python, data structures, linear algebra, calculus, probability         |
| ml-classic       | 1     | linear / logistic regression, SVM, decision tree, RF, kNN, k-means     |
| dl               | 2     | MLP, backprop, optimization, regularization, CNN, RNN, attention, Transformer |
| llm              | 3     | tokenization, embeddings, pretraining, fine-tuning, RLHF, prompting, CoT, eval |
| agent            | 4     | ReAct, tool use, memory, RAG, multi-agent, agent evaluation            |
| builder          | 5     | function calling, structured outputs, streaming, cost-opt, caching, observability, guardrails |

Foundation has the longest tail of out-edges; builder is mostly downstream
sinks. The graph is designed so that any builder-layer node has a complete
prereq closure that bottoms out at `py-basics` / `linalg-vec` /
`calculus-derivative` / `prob-basics`.

## Difficulty 1-5 legend

The legend lives in the seed JSON (`difficulty_legend`); it is treated as
authoritative.

- 1 — first exposure, finishable in one sitting with no prior context
- 2 — needs 1-2 prior nodes mastered
- 3 — requires layer foundations stable; production-relevant
- 4 — frontier-adjacent; deep prereq chain; requires hands-on synthesis
- 5 — research-level; requires reading recent papers and reproducing

The UI surfaces difficulty as roman numerals I-V to keep the manuscript
register dignified.

## Assignment types (enum)

Closed enum, lives in the seed JSON. New types should be added there before
they appear on nodes.

- derivation — pencil-and-paper derive a result
- code-from-scratch — implement in raw Python/NumPy without library shortcuts
- prove-or-counter — formal proof or counter-example
- read-canonical-paper — read and summarize the originating paper
- reproduce-result — reproduce a published result from scratch
- benchmark-compare — empirically compare two methods on a fixed task
- build-toy — small standalone implementation that runs end-to-end
- build-prod — production-quality build with error handling and tests
- trace-failure-mode — instrument and dissect a known failure
- ablation-study — methodically remove components and measure impact
- deploy-cost-budget — design under fixed cost/latency budget
- frontier-bridge-essay — short essay tying the KP to a 2025-26 frontier line

## Frontier-bridge writing convention

Each `frontier_bridges` entry is ONE sentence in the manuscript register
that grounds the KP in a 2025-26 development. The bridge is what tells the
student "this 50-year-old idea is alive in current research; here's where".

Bad: "Used in modern AI."
Good: "Low-rank decomposition is the LoRA fine-tuning kernel."
Good: "FlashAttention v3 / sliding-window / linear attention remain hot 2025 research."

`frontier_recommended_reading` lists 1-3 concrete references (author + year
+ title or doc handle). Avoid arXiv IDs alone — they age out of meaning fast.

## Engine API

```js
const cg = require('./app/lib/curriculum-graph/graph-engine');

cg.loadGraph();                       // → { layers, nodes, ... }
cg.getNode(kpId);                     // → node | null
cg.findPath(fromKpId, toKpId);        // → [id, id, ...] | null
cg.recommendNextKP(masteredKpIds, k); // → [node, ...] up to k
await cg.kpForGoal(goalText, k);      // → [{ node, score }, ...]
cg.getFrontierBridge(kpId);           // → { kpId, kpName, bridges[], reading[] } | null
await cg.buildCustomCurriculum(goalContract, targetTotalLessons);
//   → { ok, plan: { goalText, targetKpIds, kpIds, lessons[] } }
```

`findPath` uses Kahn's algorithm on the prereq closure of `toKpId`; the
output is a topological order in which a learner can walk to the target.
If `fromKpId` is null, the full closure is returned (no leading trim).

`recommendNextKP` returns nodes whose prereq_ids are ALL present in
`masteredKpIds`. Sorted by (difficulty asc, layer order asc).

`kpForGoal` currently uses a deterministic token-overlap mock. Replacement
target is the W5.1 cheap-router task type `'kp-match'` — same return shape,
swap the implementation only. The MVP is sufficient for AI/CS goals because
the seed KPs cover the field's standard vocabulary directly.

## Integration points

### Boundary with W6.1 Book Grounding

W6.1 grounds a course in a specific book corpus. The curriculum graph
provides the field-level scaffolding orthogonal to any one book. The two
are complementary:
- W6.1 supplies authoritative passages per KP.
- W6.4 supplies the prereq ordering across KPs.
The intended composition: `buildCustomCurriculum` produces a KP sequence,
W6.1 fills each KP body with grounded book passages where available.

### Boundary with W6.3 Research Radar

W6.3 polls recent arXiv / blogs / talks for newly emerging concepts.
`frontier_bridges` give it the seed claims to verify and the `kpId` to
attach new papers to. The Radar can mutate `frontier_recommended_reading`
over time; the graph structure (nodes + prereqs) stays frozen.

### Boundary with W5.2 Web Note Engine

W5.2 is user-side: the user's personal evolving knowledge graph. W6.4 is
domain-side: the curated AI/CS field shape. The two share an embedding
space at run-time (both can match a goal-text query) but never write to
each other — mastery is local to the user, KP curation is global.

### Boundary with `designSequence` (agent.js)

When the topic + goal hits the AI/CS keyword regex, `designSequence`
prefers `buildCustomCurriculum` over LLM skeleton generation. The result
is normalized into the existing `{ lessons: [{ title, learnGoal, prereqIds }] }`
shape so downstream consumers (designLesson, lessons:adapt, lesson-body
generator) need no change. `opts.disableCurriculumGraph=true` opts out for
A/B baseline runs.

## What this v1.8 does NOT include

- No other domains (math beyond AI prereqs, biology, design, writing, etc.).
- No graph editing UI — the seed is authored in JSON, reviewed in pull request.
- No user-side mastery store — `masteredKpIds` is currently passed in by the
  caller; v2.x will source from the per-vault mastery map.
- No multi-path traversal — `findPath` returns one canonical topological
  order; alternative paths through the same closure are not surfaced.
- No fork-per-user — every user sees the same graph. Personalization
  happens via `recommendNextKP` filtering, not via graph mutation.
